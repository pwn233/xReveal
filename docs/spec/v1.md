# xReveal v1 spec

xReveal is a lightweight, low-latency viewer for playing a console live through a capture card on a computer monitor, for Windows and macOS, built in Rust on GPUI Kit 0.11. This spec is the end point of the planning map ([Map: xReveal v1…](https://github.com/pwn233/xReveal/issues/2)). Each section links the decision tickets that hold the detail and the reasoning.

Words in **bold** that are capitalised (Source, Video format, Fill mode, …) are defined in [`GLOSSARY.md`](../../GLOSSARY.md). Architecture decisions are recorded in [`docs/adr/`](../adr/).

**Priority when trade-offs collide:** input-to-screen latency first, then CPU and GPU use, then memory and app size. The aim is to use about a tenth of the resources OBS uses and to be faster than it.

---

## 1. Scope

### In v1
- A live viewer only: you play through it.
- Windows (x64) and macOS (arm64, macOS 12 or later).
- One **Source** on screen at a time.
- SDR only.

### Out of v1
- Recording to a file, and streaming.
- An audio mixer, audio filters, and extra microphone sources.
- Named profiles. There is exactly one **Remembered setup**.
- HDR.
- Linux.
- Showing more than one Source at once, including picture-in-picture.
- Hardware MJPEG decode.
- Any network access beyond the opt-out, once-a-day update check and the downloads a person asks for (§2.10). A crash report goes only through the person's own browser, when they submit it (§2.11).
- Paid code signing.

### Capture cards ([#12](https://github.com/pwn233/xReveal/issues/12), [#7](https://github.com/pwn233/xReveal/issues/7))
- **Promised:** every driver-free UVC/UAC capture card, on both OSes.
- **Best effort:** driver-based cards (PCIe and older proprietary USB). On Windows they work through DirectShow. On macOS most can't work at all.
- **Every capture device the OS lists is offered**, so the user can try it.
- **Tested against:** the **Reference card** only. That is the Onten card, a MacroSilicon MS2131 (`345f:2131`), USB 2 only, serial `93869598`.
  - It has no 1080p60 mode.
  - Its usable modes are 720p60 and 1080p50. Both travel compressed (MJPEG) over USB.
  - See [#3](https://github.com/pwn233/xReveal/issues/3) and [#25](https://github.com/pwn233/xReveal/issues/25).

## 2. Product behaviour

### 2.1 Launch ([#15](https://github.com/pwn233/xReveal/issues/15), [#11](https://github.com/pwn233/xReveal/issues/11), [#30](https://github.com/pwn233/xReveal/issues/30))

**First launch (no Remembered setup yet): the Welcome screen.**
- It is a centred card picker.
- **On macOS, before the picker:**
  - **Two cards, side by side** ([#143](https://github.com/pwn233/xReveal/issues/143)): under "Let xReveal use your capture card", **Camera** is marked *Needed* ("For the picture from your capture card.") and **Microphone** *Optional* ("For the card's sound. You can play without it."). Each card has its own button, which carries its state:
    - **Allow access** asks macOS for that one only.
    - Once given, the button becomes a filled **✓ Allowed**, which does nothing.
    - If turned off, the button reads **Open System Settings**, linked straight to that privacy page.
  - **Continue without sound** shows once Camera is allowed. The screen stays until Camera is allowed and Microphone is allowed or skipped. The skip is remembered (`sound-skipped`), so it isn't asked again. Access can still be given later from the Audio tab.
  - **No sound input opens without Microphone access**: opening one would make macOS ask on the main thread and hang the app. The sound starts by itself once access is given.
  - **Locked inputs in the drawer** ([#113](https://github.com/pwn233/xReveal/issues/113), [#146](https://github.com/pwn233/xReveal/issues/146)):
    - **Input box:** without Camera access, the Source tab's **Input** is one box instead of the selector: a camera icon, "Camera access needed" (or "Camera access is off"), and one full-width button. Without Microphone access, the Audio tab's **Input** is the same box for the microphone.
    - **The button** is **Allow access** while macOS hasn't asked yet (it shows the prompt), and **Open System Settings** once it has (macOS asks only once). Access is per app, so one grant unlocks every input together. Enter on the Input row presses it.
    - **The settings that act on the input are locked too.** Without Camera access that's Video format, Buffering and Device settings…; without Microphone access, Output, Volume (with Mute) and A/V sync offset. The control is greyed out and takes no clicks, ←/→ do nothing, and Enter asks for the access. The title and hint stay as they are, with a warning triangle after the title. Hovering it (pointer cursor) shows "Allow Camera access to change this." (or Microphone) in a small tip centred above it, with an arrow at the triangle, fading in after 0.3 s. The tip is xReveal's own: GPUI Kit's animated tooltip lives in its `Root` view, which xReveal doesn't use.
    - Display, Colour and Interface stay usable: they're remembered and apply once a picture shows.
  - **Access granted while xReveal runs:** the input list is read again, because macOS can list a card without its formats before access is granted. The remembered Video format is then found as usual instead of falling back to the card's default. The sound restarts once Microphone access arrives.
- **On Windows:** there is no prompt, only Windows' privacy switches ([#176](https://github.com/pwn233/xReveal/issues/176)).
  - **Read live** from the consent store Windows keeps them in (`CapabilityAccessManager\ConsentStore\webcam` and `\microphone`, `Value` = `Allow` / `Deny`): the device-wide switch (HKLM), "Let apps access your camera" (HKCU) and "Let desktop apps access your camera" (HKCU `…\NonPackaged`). Any `Deny` turns access off.
  - **Camera off:** the Blocked screen ("Windows is blocking camera access for desktop apps", **Open Windows settings** → `ms-settings:privacy-webcam`). It also shows if opening a card fails with `E_ACCESSDENIED`. The Source tab locks the same way as on macOS (Locked inputs in the drawer, above), with **Open Windows settings** in the Input box.
  - **Microphone off:** the picture keeps going. The sound stops, a bar over the picture says "Microphone access is off, so xReveal can't play sound. Settings (Tab) › Audio turns it back on.", and the Audio tab locks the same way (`ms-settings:privacy-microphone`).
  - **Turned back on:** the input opens again, or the sound restarts, without a restart of xReveal.

**Changed by [#83](https://github.com/pwn233/xReveal/issues/83):** there is no picker page for now. With no input on screen, the centred screen shows "No input selected", or "<input> isn't connected" when the remembered one is missing, with a hint to press Tab and choose one in Settings. Only a remembered input starts by itself. The Input list starts with **None**, which shows no input and remembers that. What follows describes the picker as first built.

**How these look** ([#43](https://github.com/pwn233/xReveal/issues/43)): the same centred layout as the signal screens (§2.8). The Welcome screen ("Welcome to xReveal") and the Card-not-found picker ("<input> isn't connected") list every input plugged in, each with the Video format it would start at, and refresh the list every 2 s. Neither starts an input until it is clicked. The permission screens use `camera-off`. If only Microphone access is denied, the picture still shows, with a small notice and **Open System Settings**, because the camera is what the picture needs. A broken `setup.toml` shows its one-line notice over the Welcome screen.

**Later launches: the Remembered setup is applied automatically.**
- The window opens on the remembered monitor in the remembered **Window mode**, and the picture starts. Windowed (the default) puts the window back where it was, shrunk and moved in if it would hang off that monitor; Borderless centres it on that monitor; Fullscreen covers that monitor ([#62](https://github.com/pwn233/xReveal/issues/62)).
- **Target:** at most 1 s from launch to a live picture.

**Recognising the Source:** xReveal tries these in order:
1. The exact same OS device ID.
2. The same serial number, on any port.
3. The same model (vendor and product ID), if exactly one such card is plugged in.
4. Otherwise it shows the **Card-not-found picker**.

**Two identical cards without serial numbers:** xReveal uses the one on the remembered port if there is one, and otherwise asks. It never guesses.

**The Card-not-found picker waits for a click.** It doesn't start by itself even if the card gets plugged in while it's showing.

**After a card is picked on either screen:** the picture starts with the **Settings drawer** closed.

**Monitor:**
- Recognised by the monitor's own maker, model and serial, so it survives cable, port and arrangement changes.
- Falls back to the primary monitor if the remembered one is missing.

**Audio input:**
- Paired automatically with the same physical card's audio, matched by hardware link (Windows container ID, macOS same USB device), not by name.
- On macOS the card's serial appears in the audio device's ID, not the video device's.
- If the user picks a different input, that choice is remembered.
- If the remembered input is missing at launch, xReveal falls back to the card's own audio, shows a small notice, and keeps the user's choice for next time.

It can't be dragged; Monitor moves it. On macOS it is centred on what the menu bar and Dock leave free, which would otherwise cover the picture ([#101](https://github.com/pwn233/xReveal/issues/101)) |

| Right-click on the picture, or the edge handle | Opens or closes the drawer. The handle appears when the mouse reaches the drawer's side |
| **Esc**, or a click outside the drawer | Closes the drawer |
| Arrow keys (drawer open) | Like a TV menu: **↑/↓** move between settings (the one under the cursor is highlighted), **←/→** change it (Shift+←/→ moves sliders 10 steps), **Enter** or **Space** presses buttons and flips switches (Enter on Volume mutes). On the tab's title, **←/→** switch tabs. The highlight shows only once a key is used ([#42](https://github.com/pwn233/xReveal/issues/42)) |

A Borderless window gets its title bar back on the way in, because macOS's fullscreen needs a normal window, and becomes Borderless again on the way out. A toggle or Window setting change made while macOS is still sliding waits for the slide to end, so xReveal always ends in the mode asked for last ([#203](https://github.com/pwn233/xReveal/issues/203)). On Windows, Fullscreen is borderless and instant |
| **F3** | Shows or hides the **performance box** (the Stats overlay). Off by default, remembered ([#63](https://github.com/pwn233/xReveal/issues/63)) |

### 2.3 Settings drawer ([#19](https://github.com/pwn233/xReveal/issues/19), [#11](https://github.com/pwn233/xReveal/issues/11), [#13](https://github.com/pwn233/xReveal/issues/13))

**General behaviour:**
- A see-through panel that floats over the live picture and never pushes or shrinks it.
- Right side by default. The side can be changed (Interface tab), and is remembered.
- The same look on both OSes.
- A narrow icon rail with five tabs, showing one tab's section at a time.
- Every setting has a short, plain-language **hint line**, always visible in grey under it.
- **Everything applies live**, with no Apply button. The exception is changing the Source or Video format: that restarts the picture briefly, with a "Restarting picture…" notice.

| Tab | Settings |
|---|---|
| **Source** | **Input** (the capture card). **Video format** (resolution + FPS). **Buffering** (Off / 1 frame / 2 frames). **Device settings…** (only where the OS offers it, which in practice means Windows via DirectShow). The hint mentions HDCP. |
| **Display** | **Window** (Windowed / Borderless / Fullscreen). **Target ratio** (4:3, 16:9, 16:10, 21:9, 32:9 and Custom). **Fill mode** (Fit / Stretch / Crop / Smart stretch). **Smart stretch strength** (only shown for Smart stretch). Monitor. **Performance box**: a little screen with a tile in each corner and an "off" mark in the middle. Click a corner to show the box there, or the middle to hide it ([#83](https://github.com/pwn233/xReveal/issues/83)). When it's on, what it **Shows** (at least one item). |
| **Colour** | **Colour range** (Auto / Full / Limited). **Colour space** (Auto / BT.709 / BT.601). **Picture adjustments**: brightness, contrast and saturation, plus gamma and hue under a collapsed "More". Reset picture. |
| **Audio** | Input (defaults to the card's own audio). Output (every OS output, including the card's own audio out; defaults to the system output). Volume. Mute. **A/V sync offset**. |
| **Interface** ([#64](https://github.com/pwn233/xReveal/issues/64)) | **Theme** (System / Dark / Light; Dark, the graphite look, by default). **Accent** (violet, from the app icon and the default ([#130](https://github.com/pwn233/xReveal/issues/130)); blue, teal, green, amber, pink; each tuned per theme so text in it stays readable). A Remembered setup that already chose an accent keeps it. **Panel opacity** (60–100%, for the drawer and the performance box). **Density** (Compact / Default / Spacious): it scales the whole drawer. Base text size is 14 / 16 / 17.5 px, drawer width 340 / 380 / 430 px, rail 64 / 72 / 80 px, along with chip heights and spacing ([#83](https://github.com/pwn233/xReveal/issues/83)). Type is **IBM Plex Sans**, with **Plex Mono** for figures. Both are bundled under the SIL Open Font License (`assets/fonts`). Drawer side. Never touches the picture. |

**Motion** ([#83](https://github.com/pwn233/xReveal/issues/83)):
- The drawer slides in (320 ms, ease-out) and out (200 ms).
- **Changing its side** slides it out on the old side and back in on the new one. The rail moves across while the drawer is out of sight.
- **The edge handle** slides out from the edge and fades in as the pointer nears it, and back.
- **Hand cursor** on everything clickable, the edge handle and the sliders included. A slider's hand area reaches past the ends of its bar, where its knob hangs over ([#171](https://github.com/pwn233/xReveal/issues/171)).
- **A newly chosen chip, radio or checkbox** eases into its state over 180 ms: chips and checkboxes fill with the accent, and radio dots grow into place. This happens only right after a choice, by click or by key. When the drawer opens or another tab shows, chosen controls are drawn already settled, with no flash ([#128](https://github.com/pwn233/xReveal/issues/128)).
- **Selectors** (Source › Input and Video format, Audio › Input and Output, Display › Window, Interface › Density) are xReveal's own ([#127](https://github.com/pwn233/xReveal/issues/127)). Long names are never cut off with "…": they wrap onto more lines, both in the closed selector and in its list, so one selector can be taller than another. Its chevron stays in the middle of its height ([#172](https://github.com/pwn233/xReveal/issues/172)). The list floats right under the selector (or right above it when the window has no room below, [#156](https://github.com/pwn233/xReveal/issues/156)), over the settings below. Each entry's text lines up with the selector's own text, and the chosen one is ticked on the right, under the chevron. It closes on a choice or a click outside. ←/→ on its row steps through the same entries. (GPUI Kit's Select gives every list row the height of one measured row, so its rows can't wrap.)
- **Chips:** three or fewer short choices (up to 8 characters: Buffering, Range, Colour space, Theme, the drawer's Side) share the row in **equal widths**. Longer or more numerous ones (Target ratio, Fill mode, Performance box, monitor names) wrap, each as wide as its label. Window and Density are selectors because "Borderless", "Fullscreen" and "Spacious" don't fit a third of the drawer.

**Drawer swipe** ([#141](https://github.com/pwn233/xReveal/issues/141), decided in [#133](https://github.com/pwn233/xReveal/issues/133)):
- **What it does:** a sideways two-finger swipe on a trackpad (or Magic Mouse) pulls the drawer in, and the opposite swipe pushes it away. Fingers moving away from the drawer's side open it.
- **Fingers, not settings:** it goes by finger direction, whatever the scrolling-direction setting. On macOS the native event says whether natural scrolling turned the delta around. On Windows the delta is assumed to follow the fingers, to be checked on a precision touchpad ([#140](https://github.com/pwn233/xReveal/issues/140)).
- **When it fires:** once per gesture, the moment the fingers have moved 80 px sideways, at least twice their up-down travel, without waiting for them to lift. Momentum after the fingers lift never counts. A mouse wheel's line steps never count.
- **Where it's heard:** everywhere in the window, through a capture-phase listener, so lists and dialogs that keep a scroll to themselves can't hide it. On Windows, the drawer's own window listens too. The drawer's list scrolls only up and down, so a sideways swipe over it closes the drawer instead of moving the list.
- **Switch:** Interface › **Swipe to open settings** (On / Off), on by default. Its hint says to start in the middle of the trackpad: a swipe from the right edge opens macOS's Notification Center.

**The foot of the tab rail** ([#129](https://github.com/pwn233/xReveal/issues/129), [#186](https://github.com/pwn233/xReveal/issues/186)): the GitHub mark, which opens the repository, and the update button (§2.10), side by side.
- There's no footer under the settings, so each tab's settings use the drawer's full height.
- **No version label:** the update button's tip names the running version.
- **No Quit:** Alt+F4 / Cmd+Q and the window's close button quit.
- **No Reset all settings:** removed in [#179](https://github.com/pwn233/xReveal/issues/179). Each tab keeps its own Reset.

Starting copy for the hint lines (the other tabs are written in the same voice):
- **Target ratio:** "The shape of the picture on your screen. Pick your monitor's shape (21:9 for ultrawide) to fill it."
- **Fill mode:** "How the console's 16:9 picture fits that shape: Fit adds black bars, Stretch widens everything, Crop zooms in, Smart stretch keeps the middle natural."
- **Smart stretch strength:** "0% looks just like Stretch. Higher keeps the centre more natural and stretches the edges more."
- **Window:** "Borderless keeps the window's size with no border, centred on the screen. Fullscreen covers the whole screen. F11 switches to Fullscreen and back."
- **Monitor:** "Which screen xReveal shows on. A window moves there; Fullscreen covers it." Each screen is listed by the name the OS gives it ("Built-in Retina Display"; on Windows the monitor's own name, as Windows Settings shows it, not the driver's "Generic PnP Monitor"), the primary first. Two screens with the same name also show their size ("Mi monitor · 3440 × 1440"). A window moves to the middle of that screen, keeping its size. A Borderless window is centred on it. In Fullscreen, xReveal leaves fullscreen, moves, and covers the new screen. GPUI can't move windows or take their frame away, so these are small native calls on each OS: `NSWindow.setFrame` and `setStyleMask` (without `Titled`) on macOS, `SetWindowPos` and the window styles on Windows ([#42](https://github.com/pwn233/xReveal/issues/42), [#101](https://github.com/pwn233/xReveal/issues/101)).

### 2.4 Video format ([#4](https://github.com/pwn233/xReveal/issues/4), [#17](https://github.com/pwn233/xReveal/issues/17))

**Choosing the format:**
- The user picks resolution + FPS from the formats the Source lists live.
- Pixel format is chosen automatically and never shown, in this order: NV12, then YUY2, then MJPEG. So MJPEG is used only when the chosen resolution + FPS doesn't exist uncompressed.
- Compressed modes are not marked as such in the list.

**Default Video format** (first run, or when the remembered format is gone):
- The highest frame rate that matches the console (60), then the highest resolution at that rate.
- On the Reference card that is 720p60. 1080p50 is one click away.

**High-rate MJPEG modes** (1080p120/240, 4K60 on Elgato/AVerMedia cards):
- Allowed, but best effort.
- They may exceed the CPU budget, and v1 shows no warning about that.

### 2.5 Fill modes and Smart stretch ([#8](https://github.com/pwn233/xReveal/issues/8))

- **Fit, Stretch, Crop and Smart stretch** are four separate Fill modes. The user can switch between them at any time.
- **Smart stretch** is a smooth curve from the centre to the edges, with no seams.
  - **Smart stretch strength** runs from 0% to 100%, default 50%.
  - 0% looks exactly like Stretch.
  - 100% keeps the centre undistorted and puts all the stretch at the edges.
  - A Target ratio narrower than the Source squeezes the edges instead of stretching them.
- **The curve**, per pixel:
  - `g(v) = (1−t)·v + t·(k·v − (k−1)·v^p)`
  - `v` is the distance from the centre (0..1 of the half-width).
  - `k` = Target width ÷ Source width at equal height.
  - `t` = strength.
  - `p = min(3, 0.95·k/(k−1))` for k > 1, and `p = 3` for k < 1.
  - Reference prototype: [`prototype/smart-stretch`](https://github.com/pwn233/xReveal/tree/prototype/smart-stretch/prototypes/smart-stretch).

### 2.6 Colour ([#16](https://github.com/pwn233/xReveal/issues/16), [#3](https://github.com/pwn233/xReveal/issues/3))

- **The colour labels the OS puts on frames are ignored.** For example, macOS labels the Reference card's compressed frames BT.601 when they are really BT.709.
- **Colour space, Auto:** BT.709 for pictures 720 lines and up, BT.601 below.
- **Colour range, Auto:** assumes Full.
  - The first time a Source is shown, a one-time tip appears: "Blacks look grey? Set Range to Limited, or set your console's RGB range to Full."
  - The tip is shown once per Source.
- **Manual overrides** (Range and Colour space) are remembered **per Source**.
- **Picture adjustments** are xReveal's own. They are applied on the GPU, work identically on every card and OS, and are saved in the Remembered setup.

### 2.7 Audio ([#6](https://github.com/pwn233/xReveal/issues/6), [#14](https://github.com/pwn233/xReveal/issues/14), [#31](https://github.com/pwn233/xReveal/issues/31))

**Audio route, volume and mute** live in the Audio tab.

**A/V sync offset:**
- Range −500 to +500 ms, in 1 ms steps.
- **Default 0 ms for every card.** There are no per-card defaults.
- A positive offset delays the sound, which costs nothing.
- A negative offset delays the picture. The control then shows "+N ms input lag".
- **xReveal never delays the picture on its own.** On wired outputs the sound arrives about 10–35 ms late, which people don't notice (ITU-R BT.1359: late sound is noticed only past about 125 ms).

**Echo guard** ([#112](https://github.com/pwn233/xReveal/issues/112)): the computer's own microphone played through its own speakers makes a feedback loop that doesn't stop. xReveal never listens for it (game sound can look like feedback); it goes by which devices play.
- **When:** the input is the built-in microphone and the output is the built-in speakers, not headphones. macOS: both built-in, with the data sources `imic` and `ispk` (headphones are `hdpn`). Windows: both endpoints in the container all built-in devices share, with the form factors Microphone and Speakers (headphones and headsets have their own).
- **What happens:** the sound starts **muted**, before any sound plays, and the mute is remembered like any other, so the Audio tab shows it. The Audio tab's notice and a small bar over the picture say: "Sound muted: the Mac's microphone would echo through its own speakers. Pick the input device's own audio in Settings › Audio, or use headphones." (On Windows: "the computer's microphone".)
- **Undoing it is the person's choice:** unmuting such a route keeps it unmuted until the route changes, for that session. At the next launch it's muted again.
- **Leaving it:** when the route stops echoing (the card's own audio, headphones), the guard's mute goes by itself. A mute the person turned on themselves is never lifted.

**Bluetooth hint:** when the output is Bluetooth, or reports more than about 40 ms of latency, the Audio tab's hint reads: "Bluetooth adds about N ms of sound delay. Wired headphones or speakers keep sound in step with the picture." Nothing is changed automatically.

### 2.8 Live signal states ([#26](https://github.com/pwn233/xReveal/issues/26), [#25](https://github.com/pwn233/xReveal/issues/25))

xReveal reacts only to things it can know for certain. It never judges the content of the picture, with one soft exception: a picture that stays one flat colour earns a hint, never a screen (below).

| Situation | What the user sees and what xReveal does |
|---|---|
| The Source changes resolution or refresh rate | It adapts silently: same Target ratio and Fill mode, no restart, no message. |
| No frame for **1 s** | The **No-signal screen**: black with "No signal from <card>. Check the console is on and the HDMI cable. Black picture on a PS5? Turn off HDCP in its HDMI settings." It disappears on the next frame. Flat or black frames are shown as they are, because a card's own blank output looks the same as a black game scene. |
| The picture stays **one flat colour for 10 s** (some cards, like USB2 Video, keep sending a plain near-black picture instead of stopping when their input has no signal, [#108](https://github.com/pwn233/xReveal/issues/108)) | The picture stays. A small bar at the top asks: "Only a blank picture from <card>? Check the console is on, its HDMI cable and any HDMI switch." It goes the moment the picture shows anything. Flat means a 16×9 grid of luma samples within 3 levels of each other, so a dark scene with any detail never counts. |
| HDCP | Never detected. It is only mentioned in hints. |
| Another app changed the card's format (macOS shares the card, and the last app to open it wins) | A small notice: "Another app changed <card> to 1280×720 @ 60", with a **Restore** button. xReveal never switches back automatically. The Remembered setup keeps xReveal's own choice. |
| **Source busy** (the card refuses to open) | "<card> is being used by another app (OBS, Discord, a browser…). Close it to continue." xReveal retries every 2 s and offers "Pick another input". |
| Card unplugged mid-session | The **Card-unplugged screen**: the last frame, dimmed, with "<card> was unplugged. Waiting for it…" and "Pick another input". When the **same** Source returns, xReveal resumes automatically, with its audio. A different card is ignored. |

**How the screens look** ([#45](https://github.com/pwn233/xReveal/issues/45)): each screen without a picture puts one line icon, a title and a hint line in the centre of the window, with **Pick another input** below where it applies. That button opens the drawer on the Source tab. The screens sit on black (the Card-unplugged screen dims the last frame instead) and always use the dark palette, whatever the Theme. Icons: no input → `cable`, No signal → `monitor-off`, Card unplugged → `unplug`, Source busy → `lock`. On Windows the video surface hides while one of these screens shows, because it would cover them, so the Card-unplugged screen there is plain black. The format-changed notice stays a small bar at the top.

**Checked twice a second.** A busy or returned card is opened again at most every 2 s.

**Sound during these states:** it plays whatever arrives, and is silent while the card's audio device is gone. There is no muting and no fades.

### 2.9 What's new ([#144](https://github.com/pwn233/xReveal/issues/144), [#135](https://github.com/pwn233/xReveal/issues/135))

- **When:** once after an update. `setup.toml` remembers the last version whose What's new was seen (`whats-new-seen`). On launch, if the running version is newer and has notes, the dialog shows. A first install has nothing to compare with, so it counts its version as seen.
- **Where:** a dialog in the middle of the window over a dimmed backdrop. It's solid, so the notes read over any game.
  - **Header:** "What's new in x.y.z", with "Just updated".
  - **The notes:** a bullet list.
  - **Footer:** a quiet "Full notes on GitHub" (this version's release page) and **Got it**.
- **Closing it:** only Got it closes it, and it records the version.
- **Scrolling:** past about 260 px the list scrolls, with a fade at the top or bottom while there's more that way.
- **The notes** are this version's section of **`CHANGELOG.md`** (`## x.y.z – date`, then `- ` lines), built into the app, so no network is needed. The same section is the GitHub release body.
- **Windows:** the overlay window draws the dialog. An invisible twin in the main window, at the same place and on the same scroll position, takes the clicks and the scrolling.


### 2.10 Update available ([#145](https://github.com/pwn233/xReveal/issues/145), decided in [#138](https://github.com/pwn233/xReveal/issues/138), research [#136](https://github.com/pwn233/xReveal/issues/136))

- **The check:** once a day, xReveal asks GitHub for its latest release (`GET api.github.com/repos/pwn233/xReveal/releases/latest`).
  - **When:** only after the picture has shown, so start-up never competes with it, and every 24 h in a long session.
  - **What it sends:** `User-Agent: xReveal`, `Accept-Language: en` and `Accept`, nothing else.
  - **How:** each OS's own HTTP stack (an ephemeral `NSURLSession` on macOS, WinHTTP on Windows), so the system proxy and trusted roots apply and no crate is added. A 10 s timeout, and at most 256 KB is read.
- **Answers:** a check counts only when GitHub answers (200, or 404 for nothing published yet). Offline, rate-limited or refused shows only in the button's tip ("Couldn't reach GitHub"), and is tried again later. A version with a suffix (`-beta.1`) is never offered. `release.yml` also publishes those as prereleases, so they're never "latest".
- **The update button** sits at the bottom of the tab rail, to the right of the GitHub mark ([#186](https://github.com/pwn233/xReveal/issues/186)).
  - **A refresh icon** while this version is the latest. Hovering it shows "xReveal x.y.z" and how the last check went (not yet, checking, up to date, or couldn't reach GitHub). Pressing it asks GitHub at once, even with the switch off, and the icon pulses while it does.
  - **A download icon** in the accent colour when a newer release is out. Hovering it shows "xReveal x.y.z is out · Click to download it", its notes as bullets, and **Release notes on GitHub ↗**. The notes stop at 180 px and scroll, with a fade at the top or bottom while there's more.
  - **Pressing it downloads that version inside xReveal** ([#163](https://github.com/pwn233/xReveal/issues/163)), with a progress ring filling around the icon. The ring eases after the real progress and never fills faster than in about 0.7 s, so a fast download still shows it filling smoothly; it runs to full before the button turns into Restart ([#184](https://github.com/pwn233/xReveal/issues/184)).
    - **Checked before it's offered:** the download must match the release's `SHA256SUMS`, and on macOS the new app must be signed with the same certificate as the running one (its designated requirement, #162).
    - **Ready:** the button turns into a filled **restart** icon ("xReveal x.y.z is ready · Click to restart and update").
    - **Failed:** a failure says why in the tip, and pressing again retries.
  - **Pressing restart installs and relaunches.**
    - **macOS:** the release's `.zip` is unpacked beside the running app and the bundles are swapped. The new one opens, and it removes the old one at launch. It isn't quarantined, so there's no Gatekeeper prompt. An app run straight from a download (App Translocation) is told to move to Applications first.
    - **Windows:** the installer runs silently (`/S /RELAUNCH`). It waits for xReveal to quit, installs, and starts the new version.
  - Nothing downloads without the press: the daily check only offers.
  - **`XREVEAL_UPDATE_FEED`** points downloads at another server (`<feed>/v<version>/<asset>`) to try this before a release exists. The checksum and the signature are still checked.
  - **The tip** opens above the button with an arrow, like the lock tips. It stays while the pointer is on the button or the tip, so its link and its notes can be reached. It fades out 0.3 s after the pointer leaves both.
  - Nothing shows over the picture, and there's no "skip this version".
- **The switch:** Interface › **Check for updates** (On / Off), on by default. Its hint: "Once a day, xReveal asks GitHub whether there's a newer version. Nothing else is sent." It governs the daily check. Switching it on checks at once. Switching it off forgets an update already found; the button can still check by hand.
- **Remembered** in `setup.toml`, under `[updates]`: `check`, `last-check` (Unix seconds), and `latest` with its `notes`. The offer shows at once on the next launch, offline too.
- **Release notes:** a release's body is that version's `CHANGELOG.md` section, so it matches What's new, and `release.yml` fails without one. Each release also carries `SHA256SUMS` for its assets.

### 2.11 After a crash ([#198](https://github.com/pwn233/xReveal/issues/198), research [#193](https://github.com/pwn233/xReveal/issues/193))

Crash data stays on the computer. xReveal sends nothing itself: the issue button opens the person's browser, and only their own Submit sends anything.

**The files**, in the settings folder next to `setup.toml` (`%LOCALAPPDATA%\xReveal\`, `~/Library/Application Support/xReveal/`):
- **`running.toml`, the run marker:** version, process ID and start time. It's written at launch and removed on a clean quit, before the update restart (§2.10) and when `--report` exits. If it's still there at the next launch, the last run didn't end cleanly.
- **`last-panic.txt`:** written by a panic hook before the process unwinds or aborts. It holds the message, location, thread, backtrace, version, OS and a short setup summary. Only the latest is kept.
- **`xreveal.log`:** events only, never per frame. It records launch and quit, Source and Video format changes, signal states (§2.8), devices appearing and leaving, the update check's result, and errors. It's capped at 256 KB, with one older file kept. One plain-text line per event: `2026-11-28T12:01:29Z INFO source: USB2 Video 1920×1080@50 NV12` (UTC time, level, area, message).
- **Nothing personal** in any of them: the home folder becomes `~` in paths, a Source is named by its model, and audio device names, monitor serials and the user name are left out.
- There's no in-process crash handler and no dump writer. A crash in native code (Media Foundation, Direct3D, CoreMediaIO, Metal) is left to the OS's own report.

**On the next launch**, a leftover marker is matched to the OS's report by process ID and time:
- **Windows:** Application event 1000, falling back to `Report.wer` under both `%LOCALAPPDATA%` and `%ProgramData%` `\Microsoft\Windows\WER\`.
- **macOS:** `~/Library/Logs/DiagnosticReports/xreveal-*.ips`.

**The note** is a small bar at the top of the picture, like the format-changed notice (§2.8), never a dialog over the game:

| What was found | It says | Buttons |
|---|---|---|
| `last-panic.txt` or a matching OS report | "xReveal crashed last time. Reporting it helps fix it: the issue opens in your browser for you to check and send." | **Open an issue on GitHub**, **Show the files**, × |
| Only the marker (a kill, a forced logout or a power cut look the same) | "xReveal didn't close normally last time. If something went wrong, its log is in the settings folder." | **Show the files**, × |

- It shows only on the launch right after. × or the issue button hide it for good. Otherwise it goes after 30 s, or when the drawer opens. It never shows twice for the same run.
- When What's new is also due (§2.9), What's new shows first.
- **Show the files** reveals the settings folder in Explorer or Finder.

**The pre-filled issue:** the button opens `github.com/pwn233/xReveal/issues/new?title=…&body=…` in the browser. Nothing is uploaded or copied to the clipboard.
- **Title:** `Crash: <the panic message's first line> (<file:line>)`, or `Crash: <exception code or signal> in <faulting module>`.
- **Body:**
  1. **What were you doing?**, left empty;
  2. **Setup:** xReveal version, OS and build, Source model, Video format, Window mode, Buffering;
  3. **Crash:** the panic message, location and thread, and/or the OS report's exception, signal and faulting module, with the top 10 frames;
  4. **Log:** the last 30 lines;
  5. "Pre-filled by xReveal. Nothing was sent until you pressed Submit."
- The body is capped at about 6 KB, because GitHub refuses very long URLs. Log lines are cut first, then frames.

**For the verification cards:**
- **`XREVEAL_CRASH_TEST=panic | abort | native`** crashes xReveal 10 s after the picture shows. `native` is a deliberate access violation or SIGSEGV. Unset, it does nothing.
- **When driven** (`XREVEAL_DRIVE=1`, [#196](https://github.com/pwn233/xReveal/issues/196)), the log gets one line saying so, not one per command. `state` reports `"last_run": "crashed" | "not_clean" | "clean"`.

## 3. Technical route

### 3.1 Capture ([#4](https://github.com/pwn233/xReveal/issues/4), [#12](https://github.com/pwn233/xReveal/issues/12), [ADR 0002](../adr/0002-windows-capture-mf-first-directshow-fallback.md))

Both OSes use direct `objc2` / `windows` bindings, not `nokhwa`, which copies every frame.

**macOS:**
- AVFoundation lists the devices and their formats, and sets the chosen one on the device (`lockForConfiguration`, `activeFormat`, frame duration).
- **Frames come from the device's CoreMediaIO stream, not an `AVCaptureSession`** ([#118](https://github.com/pwn233/xReveal/issues/118)):
  - The CoreMediaIO device is the one whose UID equals AVFoundation's `uniqueID`. Its first input stream's buffer queue (`CMIOStreamCopyBufferQueue`) calls back on each frame. Frames arrive in the device's native format, usually `420v`, already decoded.
  - Sample times are converted from the stream's clock (`kCMIOStreamPropertyClock`) to host time.
  - **Why:** a session loads macOS's camera Video Effects into the app (Portrait, Reactions with their 3D scenes, face and gesture detection). In a probe that was ~195 MB and work on every frame, which an app can't turn off. The stream gives the same frames without any of it. The effect libraries still get linked in, but nothing runs or allocates.
  - With no session there's no session preset to override `activeFormat`, which was a trap with `AVCaptureSession` ([#3](https://github.com/pwn233/xReveal/issues/3)).
- Unplugging stops the stream. xReveal polls `isConnected` and opens it again when the card is back.

**Windows:**
- Capture uses the Media Foundation async Source Reader with `MF_LOW_LATENCY`, for every device MF lists.
- **DirectShow is the fallback** for devices only DirectShow sees.
- DirectShow is also used for the **Device settings** window (`ISpecifyPropertyPages` + `OleCreatePropertyFrame`). If that window can't open while MF is streaming the same device, the stream may pause while it's open.
  - As built ([#46](https://github.com/pwn233/xReveal/issues/46)): the DirectShow device is the one whose `DevicePath` equals MF's symbolic link. The button shows only when the device lists property pages, which is checked before MF opens it. The window opens on its own single-threaded COM thread, so xReveal keeps drawing. If the driver refuses while MF streams, the stream closes, the window opens again, and the stream reopens when it closes.
  - The DirectShow *capture* fallback and audio path wait for a DirectShow-only device to turn up in the hardware pass. They need a custom sink filter, because the `windows` crate has no SampleGrabber.
- DirectShow-only cards may also need a DirectShow audio path, because `cpal` can't reach a DirectShow audio pin.

**Source identity:**
- The OS device ID (MF symbolic link, AVFoundation `uniqueID`) depends on the USB port when the card has no serial.
- Store the ID, the serial and the model (vendor and product ID).

### 3.2 MJPEG ([#17](https://github.com/pwn233/xReveal/issues/17))

- **macOS** always decodes MJPEG before the app sees it, so xReveal has no decoder code there.
- **Windows:** xReveal takes the compressed MJPEG samples from MF and DirectShow and decodes them itself with **`zune-jpeg`**.
  - Output is YCbCr, uploaded once. The shader does the colour work.
  - Cost: 2.5–6 ms per 1080p frame on an M3, about 146 KB of binary.
  - Not used: MF's MJPEG Decoder MFT (YUY2-only, speed unknown) and DirectShow's MJPEG Decompressor (RGB on the CPU).
- Facts and benchmark: [`research/mjpeg-decode`](https://github.com/pwn233/xReveal/blob/research/mjpeg-decode/docs/research/mjpeg-decode.md).

### 3.3 Frame pipeline ([#24](https://github.com/pwn233/xReveal/issues/24))

**Threads:**
- Each OS has one **video thread**, which owns the GPU surface.
- The capture callback only puts the newest frame into a **single slot**, replacing any frame not yet drawn, and wakes the video thread.
- The video thread decodes MJPEG (Windows), uploads, draws and presents.
- Only the newest frame is ever decoded, so nothing queues up.

**Picture-delay stage:**
- Buffering and a negative A/V sync offset share one stage.
- It is keyed on capture timestamps.
- At zero it is bypassed entirely.

**Presenting:**
- Each frame is presented as soon as it is drawn, and the screen updates in step with the display (no tearing).
- **macOS:** the layer doesn't wait for vsync itself (`CAMetalLayer.displaySyncEnabled = false`) and has **2 drawables**. The window server composites the window at the display's refresh, so there's no tearing; the layer's own vsync only added a second wait. Measured on the built-in display: ~45 ms → ~8 ms arrival → screen ([#54](https://github.com/pwn233/xReveal/issues/54)). A third drawable let a finished frame queue behind the previous one and reach the screen a refresh later: xReveal's share was ~14 ms (p99 ~22) with 3 and is ~5 ms (p99 ~10–12) with 2, with almost no late frames, at 1080p50 on the 120 Hz built-in screen ([#56](https://github.com/pwn233/xReveal/issues/56)).
- **macOS Fullscreen is macOS's own fullscreen** ([#56](https://github.com/pwn233/xReveal/issues/56)). Metal System Trace on the built-in screen showed why: with a borderless window stretched over the screen, every screen frame was composited two refreshes ahead (`min-quanta 2`, ~15 ms compose → glass), and the video layer was never shown direct to display ("layer requires a potential offscreen render"). This held even with GPUI's layer hidden, an opaque window and no backdrop. In macOS's own fullscreen, the video layer goes direct to display, the compositor works one refresh ahead, and xReveal's share falls from ~15 ms to ~4–6.5 ms. That's with the UI and the performance box showing.
- **Windows:** a flip-model, waitable swap chain with `SetMaximumFrameLatency(1)`, presenting with vsync.
- **There is no tearing mode.** On a 60 Hz monitor waiting for the refresh can add up to a full refresh, which is accepted.
- A 50/60 fps Source on a faster monitor needs no frame-pacing logic.

**Timestamps:** every frame records capture time and present time on one host clock. They feed the Stats overlay and the latency budget.
- **macOS:** the sample-buffer PTS converted to host time, and `MTLDrawable.presentedTime`.
- **Windows:** `MFSampleExtension_DeviceTimestamp` (QPC), and DXGI `GetFrameStatistics` → `SyncQPCTime`.

**Stats overlay (F3), the "performance box"** ([#63](https://github.com/pwn233/xReveal/issues/63)):
- Hidden by default. Shown or hidden with F3 or the Display tab, and remembered.
- Sits in a chosen corner (top left by default). When the drawer is open on that side, it slides aside with the drawer, and at the bottom left it stays above the status line.
- **The bars at the top centre** (the echo and blank-picture hints, the colour tip, the format-changed and microphone notices) stack one under another, wrap at 480 pt, and stay centred in the window. While the box sits in a top corner, they share the top row with it and keep the same distance from both sides, so they never run under the box; a narrow window wraps them more ([#114](https://github.com/pwn233/xReveal/issues/114)).
- Lists any of the following, each switched on or off (all on by default):
  - Latency: capture → screen ms and xReveal's share (p50 / p99), plus launch → picture. When xReveal had to wait for Camera access first, it reads **access → picture** instead, timed from the grant: the wait was the person's, not xReveal's ([#113](https://github.com/pwn233/xReveal/issues/113)).
  - Real fps.
  - Dropped and late frames.
  - The active Video format and pixel format.

### 3.4 Rendering ([ADR 0001](../adr/0001-video-on-own-gpu-surface.md), [#9](https://github.com/pwn233/xReveal/issues/9), [#18](https://github.com/pwn233/xReveal/issues/18))

**Surfaces:**
- The picture is drawn on **xReveal's own native GPU surface**, not by GPUI. GPUI draws only the UI.
- **macOS:** a Metal layer in a native view under GPUI's content. Capture buffers come in with zero copies: each buffer's IOSurface planes are wrapped as Metal textures (`newTextureWithDescriptor:iosurface:plane:`) the first time the buffer comes round, then reused by IOSurface ID. The card cycles through a small pool; USB2 Video uses two buffers. Wrapping every frame anew through `CVMetalTextureCache` cost half of the video thread's CPU ([#118](https://github.com/pwn233/xReveal/issues/118)).
- **Windows:** a child window with its own Direct3D 11 device and swap chain. Each frame is uploaded once.
- wgpu was rejected.

**One shader pass**, written twice (MSL and HLSL), in this order:
1. Read the YUV planes (NV12 / YUY2 / zune-jpeg YCbCr).
2. Undo any range squeeze the OS applied. macOS maps the decoded compressed picture to limited range.
3. Apply the Colour space matrix and Colour range.
4. Apply the Picture adjustments.
5. Map each screen pixel back through the Fill mode (including Smart stretch).
6. Sample with **Catmull-Rom bicubic** filtering.
7. Write the output pixel.

There are no intermediate textures.

**Filtering cost** ([#56](https://github.com/pwn233/xReveal/issues/56), [#118](https://github.com/pwn233/xReveal/issues/118)): NV12 keeps each plane in its own texture, so the hardware can filter, and Catmull-Rom runs as 5 bilinear fetches per plane instead of 16 reads:
- The middle pair of taps on each axis has positive weights, so one filtered fetch between them gives both. That makes 3×3 fetches.
- The four corner fetches carry the smallest weights (products of the negative outer lobes). They are left out and the other five renormalised. The test reference does the same, and against full 16-tap Catmull-Rom the picture moves by about 3/255 at most, on hard synthetic colour edges (6/255 with strong Picture adjustments, which amplify it).
- A 1920×1080 frame drawn to the 3024×1964 Retina drawable takes 0.56–0.59 ms of GPU time (M3, median of 120): 2.7 ms with 16 reads, 0.91 ms with 9 fetches.
- The video pass is almost all of xReveal's GPU time. The GPU stays in its lowest clock state for it, where a frame takes about twice as long as in the timing test.
- YUY2 and the decoded 4:4:4 layout pack channels together, so they keep the 16-tap reads.

### 3.5 Settings UI composition ([#19](https://github.com/pwn233/xReveal/issues/19))

**macOS:** the Settings drawer is drawn by GPUI in the same window, over the video's native view.

**Windows:**
- The video's child window sits above GPUI's in-window UI, so the drawer is a **separate borderless, transparent GPUI window** (`WindowBackgroundAppearance::Transparent`, `WindowKind::PopUp`).
- **It opens hidden** ([#170](https://github.com/pwn233/xReveal/issues/170)): it's made native (owned, no frame, border, rounded corners or animations) first, then shown with the keys. Shown straight away, Windows 11 drew its 1-px window border round it for a frame: a white line along the drawer's inner edge.
- It must follow the main window: move, resize, minimise.
- It stays open when another app takes focus, as the drawer does on macOS ([#188](https://github.com/pwn233/xReveal/issues/188)): it's owned by the main window and not topmost, so it never floats over other apps. A click on the picture, Esc or Tab closes it. (It used to close whenever xReveal lost focus, from when it could float over other apps.)
- While the drawer is open, Windows may present the video on a slower path. A little extra latency only while settings are open is accepted.
- **The other overlays get a window of their own too** ([#48](https://github.com/pwn233/xReveal/issues/48)): the performance box, the colour tip, the one-line status, the one-time notice and the edge handle.
  - It's a transparent pop-up over the main window's content area, made native after opening. It's owned by the main window (not topmost), so it stays just above xReveal and minimises with it rather than floating over other apps. It never takes focus, and every mouse message passes through to the main window (`WM_NCHITTEST` → `HTTRANSPARENT`). A click on the edge handle therefore lands on the main window, which opens the drawer. The main window also places an empty copy of the handle, with the hand cursor, since the overlay window can't set the cursor ([#171](https://github.com/pwn233/xReveal/issues/171)).
  - **Focus with these windows on top** (Windows): the main window keeps its title bar lit while the drawer has the keys, as it would for a menu, and dims it only when another app is chosen. A click on the picture brings xReveal to the front, even though it reaches the main window through the overlay window, which never takes focus. Both come from one subclass of the main window (`WM_NCACTIVATE`, `WM_ACTIVATEAPP`, mouse-down → `SetForegroundWindow`).
  - It redraws from a copy of what to show, taken after each update of the main view.
  - `XREVEAL_OVERLAY_WINDOW=1` forces it on macOS for testing. There it's a child window that ignores the mouse.

### 3.6 Audio pipeline ([#6](https://github.com/pwn233/xReveal/issues/6), [#31](https://github.com/pwn233/xReveal/issues/31))

**The chain:**
- `cpal` input → a lock-free ring buffer → `cpal` output.
- A slow PI controller on the ring's fill level steers a `rubato` async resampler. This handles clock drift and rate mismatches such as 48 → 96 kHz.
- Volume and mute are done in software.
- A positive A/V sync offset is applied by raising the ring's target fill.
- Added size: about 180 KiB.

**macOS:**
- Open the output at the device's current sample rate. Otherwise `cpal` changes it system-wide.
- Ask for **128-frame** buffers.

**Windows:** use the shortest WASAPI shared-mode period the device allows (typically 10 ms). Writing our own `IAudioClient3` code for shorter periods is not in v1.

**Dropouts:** on a dropout or crackle, xReveal doubles that device's buffer and remembers the new size per device.

**As built** ([#44](https://github.com/pwn233/xReveal/issues/44)):
- The ring is xReveal's own (`src/audio/ring.rs`): one writer, one reader, atomic counters, sized for 1.5 s.
- Before playing, the ring fills to a cushion: 1.5 × (input period + output period) + 2 ms, about 10 ms with 128-frame buffers. A positive A/V sync offset is added on top.
- The PI controller moves `rubato`'s polynomial async resampler by at most ±1%. If the fill ends up more than 80 ms above target (after a stall), the excess is skipped.
- Only a dropout while sound is still arriving counts as a dropout. A silent or unplugged input doesn't.
- Doubling the buffer applies where its size was chosen (macOS, up to 2048 frames). On Windows the WASAPI default period is used.
- macOS pairs the card's audio by the serial in CoreAudio's device UID. Windows pairs it by container ID ([#71](https://github.com/pwn233/xReveal/issues/71)):
  - the video device's container is found through its symbolic link, then its device instance (CfgMgr32 `DEVPKEY_Device_ContainerId`);
  - each capture endpoint's container comes from its own device node, `SWD\MMDEVAPI\<endpoint ID>`; cpal's WASAPI device ID is that endpoint ID;
  - the container shared by all built-in devices never counts as a match.
- The Bluetooth hint uses cpal's `InterfaceType::Bluetooth`, or the output's measured delay (playback time minus callback time) above 40 ms.

### 3.7 Remembered setup storage ([#28](https://github.com/pwn233/xReveal/issues/28))

**The file:**
- One `setup.toml` per machine, never roaming.
- macOS: `~/Library/Application Support/xReveal/`. Windows: `%LOCALAPPDATA%\xReveal\`.
- It is readable by a person, but editing it by hand is not a documented workflow.

**Contents:**
- The Remembered setup: Source identity, Video format, Target ratio, Fill mode and strength, Picture adjustments, Audio route, A/V sync offset, monitor identity, drawer side.
- A table of **every Source ever seen**, keyed by identity: its Colour range and Colour space overrides, and whether its tip has been shown. This table is never trimmed.
- Audio buffer sizes per device.

**Saving:**
- About 1 s after the last change, and on quit.
- Written to a temporary file, then renamed over the old one.

**Reading:**
- The file carries `version = 1`.
- Missing fields take their defaults. Unknown fields are ignored.
- **A value xReveal doesn't understand** (a choice from a newer version, a wrong type) takes that one setting's default, and everything else in the file is kept. A one-line notice names what was reset ([#153](https://github.com/pwn233/xReveal/issues/153)).
- If the file isn't TOML at all, it is renamed to `setup.toml.bad`, the Welcome screen opens, and a one-line notice explains.

### 3.8 macOS app requirements ([#29](https://github.com/pwn233/xReveal/issues/29))

- xReveal must run as a real `.app` with `NSCameraUsageDescription` and `NSMicrophoneUsageDescription`. Without them, macOS kills the app on its first capture.
- The card's audio needs the **Microphone** permission.
- **No camera effects:** capture doesn't go through an `AVCaptureSession` (§3.1), so macOS's Video Effects (Reactions, Portrait, Studio Light) never touch the picture, and there's nothing to turn off ([#118](https://github.com/pwn233/xReveal/issues/118)).
- **Dev loop:** `cargo run` from a terminal that declares no camera usage string gets killed on capture. Use a small `.app` launched with `open` and signed with a free Apple Development (Personal Team) identity, so the permission survives rebuilds.

## 4. Performance budgets ([#10](https://github.com/pwn233/xReveal/issues/10), [#20](https://github.com/pwn233/xReveal/issues/20))

All budgets are stated for the real setup: a PS5 at 60 Hz, through the Reference card, at 1080p50 with audio, into a 180 Hz monitor.

**Windows is checked on the Windows PC** (3440×1440 @ 180 Hz; Ryzen 7 5800X, RTX 3060 Ti). First measured there with xReveal 0.1.0, PS5 through USB2 Video at 1080p50, stats overlay on: medians of the last minutes of a 20-minute Windowed soak and of 5 Fullscreen minutes ([#194](https://github.com/pwn233/xReveal/issues/194)):

| | Windowed (1711×974) | Fullscreen (3440×1440) | Budget |
|---|---|---|---|
| xReveal's share (stats overlay, one reading) | – | 3.6 ms, p99 6.5 | ≤ 8.3 ms ✅ |
| CPU, share of the machine | 0.41% | 0.36% | ≤ 5% ✅ |
| GPU (the process's busiest engine) | 1.6% | 2.2% | ≤ 10% ✅ |
| Memory (Task Manager's: the private working set) | 32.0 MB | 31.9 MB | ≤ 40 MB ✅ |
| Dedicated GPU memory | 88.7 MB | 224.8 MB | ≤ 120 / 290 MB ✅ |

- **Where the numbers come from:** Task Manager's Memory is `Process V2\Working Set - Private`, and its Dedicated GPU memory is `GPU Process Memory(pid_*)\Dedicated Usage`. Both match Task Manager to within 0.25% and can be read without admin ([#191](https://github.com/pwn233/xReveal/issues/191)). MB here are MiB, as in Task Manager.
- **Fullscreen costs GPU memory, not RAM:** +100–136 MB of dedicated GPU memory, likely the swap chain at monitor size. The private working set doesn't change.
- **Steady:** memory settles within 10 minutes. After that, the 1-minute medians wobble by 0.04–0.06 MB.

**macOS is checked on the MacBook's built-in screen** (120 Hz ProMotion, 3024×1964): there's no 180 Hz monitor for the Mac ([#56](https://github.com/pwn233/xReveal/issues/56)). Last measured there, PS5 through USB2 Video at 1080p50 ([#118](https://github.com/pwn233/xReveal/issues/118)):

| | Windowed | Fullscreen (macOS's own) | Budget |
|---|---|---|---|
| xReveal's share, p50 / p99 | 4.6–7.8 / 10–13 ms | 2.4–8 / ~15–24 ms | ≤ 8.3 ms ✅ |
| CPU | 8% of one core ≈ 0.8% of the 10-core machine | 10.7% of one core ≈ 1.1% | ≤ 5% of the machine ✅ |
| GPU (the process's share, at the GPU's lowest clock) | 7.3–7.6% | 9.6–10% | ≤ 10% ✅, just |
| Memory footprint | ~169 MB | ~194 MB | ≤ 220 / 250 MB ✅ (provisional) |
| Launch → picture | ~0.4 s | ~0.4 s | ≤ 1 s ✅ |

- **CPU units:** Activity Monitor and `top` count 100% as one core. The budget is a share of the whole machine, as Windows' Task Manager shows it.
- **GPU:** almost all of it is the video pass (§3.4). GPUI's UI is ~0.4%. Windowed, the window server spends another ~15% compositing the window, which is billed to it, not xReveal; Fullscreen goes direct to display and skips that.
- **Memory:** capture through CoreMediaIO (§3.1) took macOS's camera Video Effects out, ~330–350 MB → ~170–195 MB. Most of what's left is window drawables: two for the video layer and three for GPUI's, each the size of the window at Retina scale (~17 MB windowed, ~23 MB Fullscreen). The rest is GPU-private memory. xReveal's own Rust heap is ~4 MB (#118).

| Budget | Target | Checked by |
|---|---|---|
| Added latency (frame arrives → on screen) | ≤ half a source frame (~8.3 ms), vsync on | In-app timestamps (§3.3) |
| vs OBS (Fullscreen Projector, buffering off) | Never slower; aim for a frame faster | 240 fps phone slow-motion, several runs |
| CPU | ≤ 5% of the whole machine | Activity Monitor / Task Manager |
| GPU | ≤ 10% | Activity Monitor / Task Manager |
| Memory, Windows | ≤ 40 MB Windowed and Fullscreen | Task Manager's Memory (`Working Set - Private`) |
| GPU memory, Windows | ≤ 120 MB Windowed, ≤ 290 MB Fullscreen | Task Manager's Dedicated GPU memory (`GPU Process Memory(pid_*)\Dedicated Usage`) |
| Memory, macOS (provisional) | ≤ 220 MB Windowed, ≤ 250 MB Fullscreen | Activity Monitor's Memory (`phys_footprint`) |
| Launch → live picture | ≤ 1 s | Timestamp from process start to first presented frame |
| App size | Tracked, no cap (starter baseline: 15.3 MB stripped) | Each release |

The latency budget applies only when the A/V sync offset is ≥ 0 and Buffering is Off.

**Memory ceilings** ([#195](https://github.com/pwn233/xReveal/issues/195)):
- **Per OS, because the OSes count differently.** macOS shares memory between CPU and GPU, so its footprint already includes the window drawables. On Windows, GPU memory is separate from Task Manager's Memory, so it has a ceiling of its own.
- **For the reference hardware only:** the Windows PC's 3440×1440 monitor with a 1711×974 window, and the MacBook's built-in screen with a 1280×887 pt window. The overlay is on in both. Memory grows with the window (the drawables and the swap chain), so another monitor or window size gives other numbers. The verification runs set the window mode, the window and the overlay in `setup.toml` before launch.
- **Checked as** the highest 1-minute median in each state over the whole run, including the drawer and input-switch cycles.
- **Set at** the settled median + 25%, rounded up to the next 10 MB. The macOS ceilings come from #118's short measurement, and the first macOS baseline ([#201](https://github.com/pwn233/xReveal/issues/201)) replaces them by the same rule, up or down.
- **Leaks are judged separately**, by growth over a soak ([#192](https://github.com/pwn233/xReveal/issues/192)): Private Bytes and GPU memory on Windows, the footprint on macOS.

## 5. Build, test and CI: the Windows dry lab ([#23](https://github.com/pwn233/xReveal/issues/23))

**On the Mac:**
- `cargo check` and `cargo clippy --target x86_64-pc-windows-msvc`, as a cargo alias (`cargo check-win`) and a `bacon` job.
- Needs Homebrew `llvm` for `llvm-rc`.
- No `cargo-xwin`.

**CI** (GitHub Actions, on every PR and every push to `main`, required to pass):
- Runners: `windows-latest` and `macos-latest`.
- Steps: build, `clippy -D warnings`, `cargo test`, and the Windows build uploaded as an artifact.
- The macOS job needs full Xcode plus the Metal toolchain. The Windows job needs `fxc.exe` from the Windows SDK.

**Tests that run without a card:**
- **Pure logic, on both OSes:** format choice, Source matching, Smart stretch maths, A/V sync offset and the picture-delay stage, and `setup.toml` round-trips.
- **The Media Foundation path against video files:** synthetic, ffmpeg-generated colour-bar clips at 720p60 and 1080p50, as MJPEG and as NV12/YUY2, in Full and Limited range. The clips are committed and regenerated by a script.
- **Shared reference images for both shaders:**
  - The images cover each Colour range and Colour space, the Picture adjustments, and each Fill mode with Smart stretch at 0 / 50 / 100%.
  - HLSL runs on WARP on Windows CI.
  - MSL runs on macOS CI's paravirtual Metal device, with a local pre-push run as the fallback.
  - A small per-pixel tolerance is allowed.
- **Smoke launch:** start with no card, reach the Welcome screen or Card-not-found picker with the swap chain created, then exit.
- No virtual camera.

**Driven runs** ([#204](https://github.com/pwn233/xReveal/issues/204), decided in [#196](https://github.com/pwn233/xReveal/issues/196)): the verification cards (#197) drive xReveal through a control channel on stdin.
- **In every build, release included, and off unless `XREVEAL_DRIVE=1`.** Commands come on stdin only, with no socket, so only the process that launched xReveal can drive it. xReveal writes one line to stderr saying it's driven (the log once #205 adds it), not one per command.
- **One command per line; one answer line each** on stdout, starting `drive:`. The first is `drive: ready`.
  - `key <key>`: one of xReveal's own keys (`tab`, `escape`, `f3`, `f11`, `ctrl-cmd-f`, `up`, `down`, `left`, `right`, `shift-left`, `shift-right`, `enter`, `space`). It enters GPUI at its key bindings, so focus and the action handlers run as for a real key; only the OS's key event is skipped. It goes to the window that has xReveal's keys: the drawer's own window while it's open there (Windows, §3.5), else the main one.
  - `move <x> <y>` / `click <x> <y>`: the pointer moves to, or left-clicks at, a point in the main window's content (logical pixels), through GPUI's mouse events. A point over the drawer's own window goes to that window.
  - `state`: one JSON line: `drawer_open`, `drawer_tab`, `stats_shown` (the performance box), `window_mode`, `fullscreen`, `transition_in_progress` (macOS is still sliding into or out of Fullscreen, §2.2), `bounds`, `monitor`, `screen` (§2.8), `status`, `audio_output`, `fps`, `dropped`, `late`, `mouse`, and `last_run` (§2.11; `null` until #205).
  - `quit`: quits as Cmd+Q does.
  - Anything else answers `drive: error …`.
- Commands wait on a channel the UI awaits, not a timer: a driven xReveal sent nothing is idle.
- `scripts/driver/drive.py` is the example: it launches xReveal, runs the overlay, drawer and Fullscreen steps for a few cycles, and checks each against `state` within a time limit.

## 6. Packaging and release ([#30](https://github.com/pwn233/xReveal/issues/30))

**Signing** ([#162](https://github.com/pwn233/xReveal/issues/162)):
- **The certificate:** every macOS build is signed with one stable, self-signed certificate, **"xReveal Self-Signed"**, made once by `scripts/make-signing-cert.sh`.
- **Why it matters:** macOS ties Camera and Microphone access to the signature's designated requirement (`identifier "io.github.pwn233.xreveal" and certificate leaf = H"…"`). With one certificate that stays the same across builds and updates, so access isn't asked for again. An ad-hoc signature changed it on every build.
- **Who uses it:** `scripts/dev-app.sh` and `scripts/package-macos.sh` use it when it's in the keychain. `release.yml` imports it from the `MACOS_SIGNING_P12` and `MACOS_SIGNING_PASSWORD` secrets, and signs ad hoc, with a warning, when they're missing.
- **Not notarised:** a first install from the web still shows macOS's "unidentified developer" warning. A paid Developer ID and notarisation can replace it later in the same place.
- **Windows** is unchanged: its privacy settings aren't tied to the exe's signature.

**App icon** ([#130](https://github.com/pwn233/xReveal/issues/130)): a purple rounded square with a lavender "XL", drawn as a vector in `assets/icon/xreveal.svg`. `scripts/make-icons.sh` renders it into `packaging/macos/AppIcon.icns` (the .app's `CFBundleIconFile`) and `packaging/windows/xreveal.ico` (embedded in the exe by `build.rs` and used by the installer). The generated files are committed, so builds never need the script.

**Licence:** MIT OR Apache-2.0.

**Distribution:** GitHub Releases only. No Homebrew, winget or Store for now.

**Assets per release:** GitHub's own source archives, plus:

| OS | Installer | Portable |
|---|---|---|
| macOS (arm64, macOS 12+) | `.dmg` | `.zip` of the `.app` |
| Windows (x64, built with `+crt-static`) | Per-user installer (no admin, installs to `%LOCALAPPDATA%\Programs\xReveal`, Start-menu entry) | `.zip` with the `.exe` |

**Builds:** a release is started by hand: Actions › Release › Run workflow, naming an existing `v*` tag and confirming with `release@<tag>` (e.g. `release@v1.0.0`). CI builds that tag and attaches the assets to a GitHub Release ([#47](https://github.com/pwn233/xReveal/issues/47)). It uses each platform's standard tools rather than `cargo-packager`, which keeps every step visible in two small scripts:
- `scripts/package-macos.sh`: the `.app` (the same Info.plist as development), an ad-hoc `codesign`, `ditto` for the zip, and `hdiutil` for the `.dmg` with an Applications link.
- `scripts/package-windows.ps1`: a `+crt-static` release build, the portable zip, and an NSIS installer (`packaging/windows/installer.nsi`). The installer is per user (`RequestExecutionLevel user`), installs to `%LOCALAPPDATA%\Programs\xReveal`, adds a Start-menu entry, and registers an uninstaller under HKCU that leaves the Remembered setup in place.
- The tag must already be pushed, must not be released yet, and must match `Cargo.toml`'s version at that tag. Pushing a tag publishes nothing. Pull requests that touch packaging build the assets as CI artifacts, so the pipeline is checked before any release.

**Signing:** none paid in v1.
- macOS gets an ad-hoc signature. Users approve it once via System Settings › Privacy & Security › Open Anyway. macOS may ask for the permissions again after each update.
- Windows builds are unsigned. SmartScreen shows "Run anyway". **Smart App Control blocks unsigned apps outright.**
- The README documents both workarounds.
- Paid signing is reconsidered when xReveal goes beyond GitHub.

## 7. Release gate: the Windows hardware pass ([#23](https://github.com/pwn233/xReveal/issues/23), [#21](https://github.com/pwn233/xReveal/issues/21))

Windows v1 is not called "supported" until one pass on a real Windows PC with the Reference card has checked these. `xreveal --report` records step 1 and the IDs in one go, including a 5-second capture with frame pacing (gap median, p99, max, late or missing frames):

1. Record what the Reference card delivers through MF and DirectShow ([#21](https://github.com/pwn233/xReveal/issues/21)'s list):
   - formats, and whether MJPEG is exposed;
   - pacing;
   - colour range and matrix;
   - the Card settings window;
   - the audio device;
   - the IDs.
2. The latency and performance budgets (§4).
3. The DirectShow fallback.
4. Card settings opening during streaming.
5. Audio pairing with the card.
6. Monitor recognition.
7. The transparent Settings drawer window over a real swap chain.
8. MJPEG decode cost on x86. If it breaks the budget on the Reference card, reconsider hardware decode.

Coding never waits for this pass.
