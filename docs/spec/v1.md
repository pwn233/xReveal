# xReveal v1 spec

xReveal is a lightweight, low-latency viewer for playing a console live through a capture card on a computer monitor, for Windows and macOS, built in Rust on GPUI Kit 0.11. This spec is the end point of the planning map ([Map: xReveal v1…](https://github.com/pwn233/xReveal/issues/2)). Each section links the decision tickets that hold the detail and the reasoning.

Words in **bold** that are capitalised (Source, Video format, Fill mode, …) are defined in [`GLOSSARY.md`](../../GLOSSARY.md). Architecture decisions are recorded in [`docs/adr/`](../adr/).

**Priority when trade-offs collide:** input-to-screen latency first, then CPU and GPU use, then memory and app size. The aim is to use about a tenth of the resources OBS uses and to be faster than it.

---

## 1. Scope

### In v1
- A live viewer only: you play through it.
- Windows (x64) and macOS (arm64, macOS 12 or later).
- One **Source** on screen at a time.
- SDR only.

### Out of v1
- Recording to a file, and streaming.
- An audio mixer, audio filters, and extra microphone sources.
- Named profiles. There is exactly one **Remembered setup**.
- HDR.
- Linux.
- Showing more than one Source at once, including picture-in-picture.
- Hardware MJPEG decode.
- An auto-updater, or any network access.
- Paid code signing.

### Capture cards ([#12](https://github.com/pwn233/xReveal/issues/12), [#7](https://github.com/pwn233/xReveal/issues/7))
- **Promised:** every driver-free UVC/UAC capture card, on both OSes.
- **Best effort:** driver-based cards (PCIe and older proprietary USB). On Windows they work through DirectShow. On macOS most can't work at all.
- **Every capture device the OS lists is offered**, so the user can try it.
- **Tested against:** the **Reference card** only. That is the Onten card, a MacroSilicon MS2131 (`345f:2131`), USB 2 only, serial `93869598`.
  - It has no 1080p60 mode.
  - Its usable modes are 720p60 and 1080p50. Both travel compressed (MJPEG) over USB.
  - See [#3](https://github.com/pwn233/xReveal/issues/3) and [#25](https://github.com/pwn233/xReveal/issues/25).

## 2. Product behaviour

### 2.1 Launch ([#15](https://github.com/pwn233/xReveal/issues/15), [#11](https://github.com/pwn233/xReveal/issues/11), [#30](https://github.com/pwn233/xReveal/issues/30))

**First launch (no Remembered setup yet): the Welcome screen.**
- It is a centred card picker.
- **On macOS, before the picker:**
  - The screen explains first: "xReveal needs Camera access for the picture and Microphone access for the sound. macOS will ask twice."
  - An **Allow access** button then triggers both OS prompts, one after the other.
  - If either permission is denied, a panel explains what is missing and offers **Open System Settings**, linked straight to that privacy page.
- **On Windows:** there is no prompt. If Windows' global "desktop apps" privacy switch blocks capture (Media Foundation returns `E_ACCESSDENIED`), a panel says "Windows is blocking camera / microphone access for desktop apps" and offers **Open Windows settings** (`ms-settings:privacy-webcam` / `privacy-microphone`).

**Later launches: the Remembered setup is applied automatically.**
- The window opens on the remembered monitor in the remembered **Window mode**, and the picture starts. Windowed (the default) puts the window back where it was; Fullscreen covers that monitor ([#62](https://github.com/pwn233/xReveal/issues/62)).
- **Target:** at most 1 s from launch to a live picture.

**Recognising the Source:** xReveal tries these in order:
1. The exact same OS device ID.
2. The same serial number, on any port.
3. The same model (vendor and product ID), if exactly one such card is plugged in.
4. Otherwise it shows the **Card-not-found picker**.

**Two identical cards without serial numbers:** xReveal uses the one on the remembered port if there is one, and otherwise asks. It never guesses.

**The Card-not-found picker waits for a click.** It doesn't start by itself even if the card gets plugged in while it's showing.

**After a card is picked on either screen:** the picture starts with the **Settings drawer** closed.

**Monitor:**
- Recognised by the monitor's own maker, model and serial, so it survives cable, port and arrangement changes.
- Falls back to the primary monitor if the remembered one is missing.

**Audio input:**
- Paired automatically with the same physical card's audio, matched by hardware link (Windows container ID, macOS same USB device), not by name.
- On macOS the card's serial appears in the audio device's ID, not the video device's.
- If the user picks a different input, that choice is remembered.
- If the remembered input is missing at launch, xReveal falls back to the card's own audio, shows a small notice, and keeps the user's choice for next time.

### 2.2 Presentation and keys ([#11](https://github.com/pwn233/xReveal/issues/11), [#24](https://github.com/pwn233/xReveal/issues/24))

| Key or action | Effect |
|---|---|

| **Tab** | Toggles the Settings drawer: opens it, and closes it even while it's open |
| Right-click on the picture, or the edge handle | Opens or closes the drawer. The handle appears when the mouse reaches the drawer's side |
| **Esc**, or a click outside the drawer | Closes the drawer |
| Arrow keys (drawer open) | Move between controls |
| **F11** | Toggles Windowed / Fullscreen, the same as the Window setting, and is remembered |
| **F3** | Shows or hides the **performance box** (the Stats overlay). Off by default, remembered ([#63](https://github.com/pwn233/xReveal/issues/63)) |
| Cmd+Q / Alt+F4, the window's close button, or **Quit xReveal** in the drawer | Quit |

### 2.3 Settings drawer ([#19](https://github.com/pwn233/xReveal/issues/19), [#11](https://github.com/pwn233/xReveal/issues/11), [#13](https://github.com/pwn233/xReveal/issues/13))

**General behaviour:**
- A see-through panel that floats over the live picture and never pushes or shrinks it.
- Right side by default. The side can be changed (Interface tab), and is remembered.
- The same look on both OSes.
- A narrow icon rail with five tabs, showing one tab's section at a time.
- Every setting has a short, plain-language **hint line**, always visible in grey under it.
- **Everything applies live**, with no Apply button. The exception is changing the Source or Video format: that restarts the picture briefly, with a "Restarting picture…" notice.

| Tab | Settings |
|---|---|
| **Source** | **Input** (the capture card). **Video format** (resolution + FPS). **Buffering** (Off / 1 frame / 2 frames). **Card settings…** (only where the OS offers it, which in practice means Windows via DirectShow). The hint mentions HDCP. |
| **Display** | **Window** (Windowed / Fullscreen). **Target ratio** (4:3, 16:9, 16:10, 21:9, 32:9 and Custom). **Fill mode** (Fit / Stretch / Crop / Smart stretch). **Smart stretch strength** (only shown for Smart stretch). Monitor. **Performance box** (Off / On; when on, its **Corner** and what it **Shows**). |
| **Colour** | **Colour range** (Auto / Full / Limited). **Colour space** (Auto / BT.709 / BT.601). **Picture adjustments**: brightness, contrast and saturation, plus gamma and hue under a collapsed "More". Reset picture. |
| **Audio** | Input (defaults to the card's own audio). Output (every OS output, including the card's own audio out; defaults to the system output). Volume. Mute. **A/V sync offset**. |
| **Interface** ([#64](https://github.com/pwn233/xReveal/issues/64)) | **Theme** (System / Dark / Light; Dark, the graphite look, by default). **Accent** (blue, teal, green, amber, pink; each tuned per theme so text in it stays readable). **Panel opacity** (60–100%, for the drawer and the performance box). **Density** (Compact / Default / Spacious). Drawer side. Never touches the picture. |

**Reset all settings** sits at the bottom of the drawer, with an inline confirm step. It clears the Remembered setup and every per-Source entry, then shows the Welcome screen.

Starting copy for the hint lines (the other tabs are written in the same voice):
- **Target ratio:** "The shape of the picture on your screen. Pick your monitor's shape (21:9 for ultrawide) to fill it."
- **Fill mode:** "How the console's 16:9 picture fits that shape: Fit adds black bars, Stretch widens everything, Crop zooms in, Smart stretch keeps the middle natural."
- **Smart stretch strength:** "0% looks just like Stretch. Higher keeps the centre more natural and stretches the edges more."
- **Window:** "Fullscreen covers the whole screen with no border. F11 switches between them."
- **Monitor:** "Which screen xReveal goes fullscreen on."

### 2.4 Video format ([#4](https://github.com/pwn233/xReveal/issues/4), [#17](https://github.com/pwn233/xReveal/issues/17))

**Choosing the format:**
- The user picks resolution + FPS from the formats the Source lists live.
- Pixel format is chosen automatically and never shown, in this order: NV12, then YUY2, then MJPEG. So MJPEG is used only when the chosen resolution + FPS doesn't exist uncompressed.
- Compressed modes are not marked as such in the list.

**Default Video format** (first run, or when the remembered format is gone):
- The highest frame rate that matches the console (60), then the highest resolution at that rate.
- On the Reference card that is 720p60. 1080p50 is one click away.

**High-rate MJPEG modes** (1080p120/240, 4K60 on Elgato/AVerMedia cards):
- Allowed, but best effort.
- They may exceed the CPU budget, and v1 shows no warning about that.

### 2.5 Fill modes and Smart stretch ([#8](https://github.com/pwn233/xReveal/issues/8))

- **Fit, Stretch, Crop and Smart stretch** are four separate Fill modes. The user can switch between them at any time.
- **Smart stretch** is a smooth curve from the centre to the edges, with no seams.
  - **Smart stretch strength** runs from 0% to 100%, default 50%.
  - 0% looks exactly like Stretch.
  - 100% keeps the centre undistorted and puts all the stretch at the edges.
  - A Target ratio narrower than the Source squeezes the edges instead of stretching them.
- **The curve**, per pixel:
  - `g(v) = (1−t)·v + t·(k·v − (k−1)·v^p)`
  - `v` is the distance from the centre (0..1 of the half-width).
  - `k` = Target width ÷ Source width at equal height.
  - `t` = strength.
  - `p = min(3, 0.95·k/(k−1))` for k > 1, and `p = 3` for k < 1.
  - Reference prototype: [`prototype/smart-stretch`](https://github.com/pwn233/xReveal/tree/prototype/smart-stretch/prototypes/smart-stretch).

### 2.6 Colour ([#16](https://github.com/pwn233/xReveal/issues/16), [#3](https://github.com/pwn233/xReveal/issues/3))

- **The colour labels the OS puts on frames are ignored.** For example, macOS labels the Reference card's compressed frames BT.601 when they are really BT.709.
- **Colour space, Auto:** BT.709 for pictures 720 lines and up, BT.601 below.
- **Colour range, Auto:** assumes Full.
  - The first time a Source is shown, a one-time tip appears: "Blacks look grey? Set Range to Limited, or set your console's RGB range to Full."
  - The tip is shown once per Source.
- **Manual overrides** (Range and Colour space) are remembered **per Source**.
- **Picture adjustments** are xReveal's own. They are applied on the GPU, work identically on every card and OS, and are saved in the Remembered setup.

### 2.7 Audio ([#6](https://github.com/pwn233/xReveal/issues/6), [#14](https://github.com/pwn233/xReveal/issues/14), [#31](https://github.com/pwn233/xReveal/issues/31))

**Audio route, volume and mute** live in the Audio tab.

**A/V sync offset:**
- Range −500 to +500 ms, in 1 ms steps.
- **Default 0 ms for every card.** There are no per-card defaults.
- A positive offset delays the sound, which costs nothing.
- A negative offset delays the picture. The control then shows "+N ms input lag".
- **xReveal never delays the picture on its own.** On wired outputs the sound arrives about 10–35 ms late, which people don't notice (ITU-R BT.1359: late sound is noticed only past about 125 ms).

**Bluetooth hint:** when the output is Bluetooth, or reports more than about 40 ms of latency, the Audio tab's hint reads: "Bluetooth adds about N ms of sound delay. Wired headphones or speakers keep sound in step with the picture." Nothing is changed automatically.

### 2.8 Live signal states ([#26](https://github.com/pwn233/xReveal/issues/26), [#25](https://github.com/pwn233/xReveal/issues/25))

xReveal reacts only to things it can know for certain. It never judges the content of the picture.

| Situation | What the user sees and what xReveal does |
|---|---|
| The Source changes resolution or refresh rate | It adapts silently: same Target ratio and Fill mode, no restart, no message. |
| No frame for **1 s** | The **No-signal screen**: black with "No signal from <card>. Check the console is on and the HDMI cable. Black picture on a PS5? Turn off HDCP in its HDMI settings." It disappears on the next frame. Flat or black frames are shown as they are, because a card's own blank output looks the same as a black game scene. |
| HDCP | Never detected. It is only mentioned in hints. |
| Another app changed the card's format (macOS shares the card, and the last app to open it wins) | A small notice: "Another app changed <card> to 1280×720 @ 60", with a **Restore** button. xReveal never switches back automatically. The Remembered setup keeps xReveal's own choice. |
| **Source busy** (the card refuses to open) | "<card> is being used by another app (OBS, Discord, a browser…). Close it to continue." xReveal retries every 2 s and offers "Pick another input". |
| Card unplugged mid-session | The **Card-unplugged screen**: the last frame, dimmed, with "<card> was unplugged. Waiting for it…" and "Pick another input". When the **same** Source returns, xReveal resumes automatically, with its audio. A different card is ignored. |

**How the screens look** ([#45](https://github.com/pwn233/xReveal/issues/45)): each screen without a picture puts one line icon, a title and a hint line in the centre of the window, with **Pick another input** below where it applies. That button opens the drawer on the Source tab. The screens sit on black (the Card-unplugged screen dims the last frame instead) and always use the dark palette, whatever the Theme. Icons: no input → `cable`, No signal → `monitor-off`, Card unplugged → `unplug`, Source busy → `lock`. On Windows the video surface hides while one of these screens shows, because it would cover them, so the Card-unplugged screen there is plain black. The format-changed notice stays a small bar at the top.

**Checked twice a second.** A busy or returned card is opened again at most every 2 s.

**Sound during these states:** it plays whatever arrives, and is silent while the card's audio device is gone. There is no muting and no fades.

## 3. Technical route

### 3.1 Capture ([#4](https://github.com/pwn233/xReveal/issues/4), [#12](https://github.com/pwn233/xReveal/issues/12), [ADR 0002](../adr/0002-windows-capture-mf-first-directshow-fallback.md))

Both OSes use direct `objc2` / `windows` bindings, not `nokhwa`, which copies every frame.

**macOS:**
- Capture uses AVFoundation `AVCaptureVideoDataOutput` with `alwaysDiscardsLateVideoFrames = true` and `videoSettings = [:]`, so it gets the device's native format, usually `420v`. Asking for `nil` would give `2vuy` and add a conversion.
- **Trap:** the session preset silently overrides `activeFormat`. Hold `lockForConfiguration()` across `startRunning()`.
- On unplug, AVFoundation sends `AVCaptureDeviceWasDisconnected` and the session runtime error −11808. On re-plug it sends `AVCaptureDeviceWasConnected`. Rebuild the session then; frames returned 0.1–0.35 s after the notification.

**Windows:**
- Capture uses the Media Foundation async Source Reader with `MF_LOW_LATENCY`, for every device MF lists.
- **DirectShow is the fallback** for devices only DirectShow sees.
- DirectShow is also used for the **Card settings** window (`ISpecifyPropertyPages` + `OleCreatePropertyFrame`). If that window can't open while MF is streaming the same device, the stream may pause while it's open.
- DirectShow-only cards may also need a DirectShow audio path, because `cpal` can't reach a DirectShow audio pin.

**Source identity:**
- The OS device ID (MF symbolic link, AVFoundation `uniqueID`) depends on the USB port when the card has no serial.
- Store the ID, the serial and the model (vendor and product ID).

### 3.2 MJPEG ([#17](https://github.com/pwn233/xReveal/issues/17))

- **macOS** always decodes MJPEG before the app sees it, so xReveal has no decoder code there.
- **Windows:** xReveal takes the compressed MJPEG samples from MF and DirectShow and decodes them itself with **`zune-jpeg`**.
  - Output is YCbCr, uploaded once. The shader does the colour work.
  - Cost: 2.5–6 ms per 1080p frame on an M3, about 146 KB of binary.
  - Not used: MF's MJPEG Decoder MFT (YUY2-only, speed unknown) and DirectShow's MJPEG Decompressor (RGB on the CPU).
- Facts and benchmark: [`research/mjpeg-decode`](https://github.com/pwn233/xReveal/blob/research/mjpeg-decode/docs/research/mjpeg-decode.md).

### 3.3 Frame pipeline ([#24](https://github.com/pwn233/xReveal/issues/24))

**Threads:**
- Each OS has one **video thread**, which owns the GPU surface.
- The capture callback only puts the newest frame into a **single slot**, replacing any frame not yet drawn, and wakes the video thread.
- The video thread decodes MJPEG (Windows), uploads, draws and presents.
- Only the newest frame is ever decoded, so nothing queues up.

**Picture-delay stage:**
- Buffering and a negative A/V sync offset share one stage.
- It is keyed on capture timestamps.
- At zero it is bypassed entirely.

**Presenting:**
- Each frame is presented as soon as it is drawn, and the screen updates in step with the display (no tearing).
- **macOS:** the layer doesn't wait for vsync itself (`CAMetalLayer.displaySyncEnabled = false`) and has 3 drawables, so drawing never waits for one. The window server composites the window at the display's refresh, so there's no tearing; the layer's own vsync only added a second wait. Measured on the built-in display: ~45 ms → ~8 ms arrival → screen ([#54](https://github.com/pwn233/xReveal/issues/54)).
- **Windows:** a flip-model, waitable swap chain with `SetMaximumFrameLatency(1)`, presenting with vsync.
- **There is no tearing mode.** On a 60 Hz monitor waiting for the refresh can add up to a full refresh, which is accepted.
- A 50/60 fps Source on a faster monitor needs no frame-pacing logic.

**Timestamps:** every frame records capture time and present time on one host clock. They feed the Stats overlay and the latency budget.
- **macOS:** the sample-buffer PTS converted to host time, and `MTLDrawable.presentedTime`.
- **Windows:** `MFSampleExtension_DeviceTimestamp` (QPC), and DXGI `GetFrameStatistics` → `SyncQPCTime`.

**Stats overlay (F3), the "performance box"** ([#63](https://github.com/pwn233/xReveal/issues/63)):
- Hidden by default. Shown or hidden with F3 or the Display tab, and remembered.
- Sits in a chosen corner (top left by default). When the drawer is open on that side, it slides aside with the drawer, and at the bottom left it stays above the status line.
- Lists any of the following, each switched on or off (all on by default):
  - Latency: capture → screen ms and xReveal's share (p50 / p99), plus launch → picture.
  - Real fps.
  - Dropped and late frames.
  - The active Video format and pixel format.

### 3.4 Rendering ([ADR 0001](../adr/0001-video-on-own-gpu-surface.md), [#9](https://github.com/pwn233/xReveal/issues/9), [#18](https://github.com/pwn233/xReveal/issues/18))

**Surfaces:**
- The picture is drawn on **xReveal's own native GPU surface**, not by GPUI. GPUI draws only the UI.
- **macOS:** a Metal layer in a native view under GPUI's content. Capture buffers come in with zero copies through `CVMetalTextureCache`.
- **Windows:** a child window with its own Direct3D 11 device and swap chain. Each frame is uploaded once.
- wgpu was rejected.

**One shader pass**, written twice (MSL and HLSL), in this order:
1. Read the YUV planes (NV12 / YUY2 / zune-jpeg YCbCr).
2. Undo any range squeeze the OS applied. macOS maps the decoded compressed picture to limited range.
3. Apply the Colour space matrix and Colour range.
4. Apply the Picture adjustments.
5. Map each screen pixel back through the Fill mode (including Smart stretch).
6. Sample with **Catmull-Rom bicubic** filtering.
7. Write the output pixel.

There are no intermediate textures.

### 3.5 Settings UI composition ([#19](https://github.com/pwn233/xReveal/issues/19))

**macOS:** the Settings drawer is drawn by GPUI in the same window, over the video's native view.

**Windows:**
- The video's child window sits above GPUI's in-window UI, so the drawer is a **separate borderless, transparent GPUI window** (`WindowBackgroundAppearance::Transparent`, `WindowKind::PopUp`).
- It must follow the main window: move, resize, minimise.
- It must hide when the app loses focus.
- While the drawer is open, Windows may present the video on a slower path. A little extra latency only while settings are open is accepted.

### 3.6 Audio pipeline ([#6](https://github.com/pwn233/xReveal/issues/6), [#31](https://github.com/pwn233/xReveal/issues/31))

**The chain:**
- `cpal` input → a lock-free ring buffer → `cpal` output.
- A slow PI controller on the ring's fill level steers a `rubato` async resampler. This handles clock drift and rate mismatches such as 48 → 96 kHz.
- Volume and mute are done in software.
- A positive A/V sync offset is applied by raising the ring's target fill.
- Added size: about 180 KiB.

**macOS:**
- Open the output at the device's current sample rate. Otherwise `cpal` changes it system-wide.
- Ask for **128-frame** buffers.

**Windows:** use the shortest WASAPI shared-mode period the device allows (typically 10 ms). Writing our own `IAudioClient3` code for shorter periods is not in v1.

**Dropouts:** on a dropout or crackle, xReveal doubles that device's buffer and remembers the new size per device.

### 3.7 Remembered setup storage ([#28](https://github.com/pwn233/xReveal/issues/28))

**The file:**
- One `setup.toml` per machine, never roaming.
- macOS: `~/Library/Application Support/xReveal/`. Windows: `%LOCALAPPDATA%\xReveal\`.
- It is readable by a person, but editing it by hand is not a documented workflow.

**Contents:**
- The Remembered setup: Source identity, Video format, Target ratio, Fill mode and strength, Picture adjustments, Audio route, A/V sync offset, monitor identity, drawer side.
- A table of **every Source ever seen**, keyed by identity: its Colour range and Colour space overrides, and whether its tip has been shown. This table is never trimmed.
- Audio buffer sizes per device.

**Saving:**
- About 1 s after the last change, and on quit.
- Written to a temporary file, then renamed over the old one.

**Reading:**
- The file carries `version = 1`.
- Missing fields take their defaults. Unknown fields are ignored.
- If the file can't be read at all, it is renamed to `setup.toml.bad`, the Welcome screen opens, and a one-line notice explains.

### 3.8 macOS app requirements ([#29](https://github.com/pwn233/xReveal/issues/29))

- xReveal must run as a real `.app` with `NSCameraUsageDescription` and `NSMicrophoneUsageDescription`. Without them, macOS kills the app on its first capture.
- The card's audio needs the **Microphone** permission.
- **Dev loop:** `cargo run` from a terminal that declares no camera usage string gets killed on capture. Use a small `.app` launched with `open` and signed with a free Apple Development (Personal Team) identity, so the permission survives rebuilds.

## 4. Performance budgets ([#10](https://github.com/pwn233/xReveal/issues/10), [#20](https://github.com/pwn233/xReveal/issues/20))

All budgets are stated for the real setup: a PS5 at 60 Hz, through the Reference card, at 1080p50 with audio, into a 180 Hz monitor.

| Budget | Target | Checked by |
|---|---|---|
| Added latency (frame arrives → on screen) | ≤ half a source frame (~8.3 ms), vsync on | In-app timestamps (§3.3) |
| vs OBS (Fullscreen Projector, buffering off) | Never slower; aim for a frame faster | 240 fps phone slow-motion, several runs |
| CPU | ≤ 5% of the whole machine | Activity Monitor / Task Manager |
| GPU | ≤ 10% | Activity Monitor / Task Manager |
| Memory | ≤ 100 MB | OS memory footprint |
| Launch → live picture | ≤ 1 s | Timestamp from process start to first presented frame |
| App size | Tracked, no cap (starter baseline: 15.3 MB stripped) | Each release |

The latency budget applies only when the A/V sync offset is ≥ 0 and Buffering is Off.

## 5. Build, test and CI: the Windows dry lab ([#23](https://github.com/pwn233/xReveal/issues/23))

**On the Mac:**
- `cargo check` and `cargo clippy --target x86_64-pc-windows-msvc`, as a cargo alias (`cargo check-win`) and a `bacon` job.
- Needs Homebrew `llvm` for `llvm-rc`.
- No `cargo-xwin`.

**CI** (GitHub Actions, on every PR and every push to `main`, required to pass):
- Runners: `windows-latest` and `macos-latest`.
- Steps: build, `clippy -D warnings`, `cargo test`, and the Windows build uploaded as an artifact.
- The macOS job needs full Xcode plus the Metal toolchain. The Windows job needs `fxc.exe` from the Windows SDK.

**Tests that run without a card:**
- **Pure logic, on both OSes:** format choice, Source matching, Smart stretch maths, A/V sync offset and the picture-delay stage, and `setup.toml` round-trips.
- **The Media Foundation path against video files:** synthetic, ffmpeg-generated colour-bar clips at 720p60 and 1080p50, as MJPEG and as NV12/YUY2, in Full and Limited range. The clips are committed and regenerated by a script.
- **Shared reference images for both shaders:**
  - The images cover each Colour range and Colour space, the Picture adjustments, and each Fill mode with Smart stretch at 0 / 50 / 100%.
  - HLSL runs on WARP on Windows CI.
  - MSL runs on macOS CI's paravirtual Metal device, with a local pre-push run as the fallback.
  - A small per-pixel tolerance is allowed.
- **Smoke launch:** start with no card, reach the Welcome screen or Card-not-found picker with the swap chain created, then exit.
- No virtual camera.

## 6. Packaging and release ([#30](https://github.com/pwn233/xReveal/issues/30))

**Licence:** MIT OR Apache-2.0.

**Distribution:** GitHub Releases only. No Homebrew, winget or Store for now.

**Assets per release:** GitHub's own source archives, plus:

| OS | Installer | Portable |
|---|---|---|
| macOS (arm64, macOS 12+) | `.dmg` | `.zip` of the `.app` |
| Windows (x64, built with `+crt-static`) | Per-user installer (no admin, installs to `%LOCALAPPDATA%\Programs\xReveal`, Start-menu entry) | `.zip` with the `.exe` |

**Builds:** CI builds every `v*` tag with `cargo-packager` and attaches the assets to a GitHub Release.

**Signing:** none paid in v1.
- macOS gets an ad-hoc signature. Users approve it once via System Settings › Privacy & Security › Open Anyway. macOS may ask for the permissions again after each update.
- Windows builds are unsigned. SmartScreen shows "Run anyway". **Smart App Control blocks unsigned apps outright.**
- The README documents both workarounds.
- Paid signing is reconsidered when xReveal goes beyond GitHub.

## 7. Release gate: the Windows hardware pass ([#23](https://github.com/pwn233/xReveal/issues/23), [#21](https://github.com/pwn233/xReveal/issues/21))

   - the audio device;
   - the IDs.

3. The DirectShow fallback.
4. Card settings opening during streaming.
5. Audio pairing with the card.
6. Monitor recognition.

Coding never waits for this pass.
